# 2026-10-29 — From a toy RAG to an evaluation-driven baseline

*First entry. It covers the whole project so far, from 8 to 29 October 2026.*

## Why this project

Over the last few months I have been thinking about how software engineering — and engineering in general — is changing with the rise of AI. What draws me in is everything around plugging AI into production systems: how to monitor it, how to evaluate it, what good practices look like, and how to optimise costs so a company spends as few tokens as possible. That is the skill set of an AI engineer, and it is what I want to grow into.

A few months ago I did not know what RAG was. I learned it is a key pattern for companies with large document bases: how can an LLM that was never trained on a company's documents quickly find answers in them? I decided to learn it by building one from scratch: **Production RAG**.

A RAG system has two halves: **retrieval** (finding the right passages for a question) and **generation** (writing the answer from those passages).

## What I did

- **First pipeline (8–11 Oct)** on three made-up Markdown documents: chunking, local embeddings (`fastembed`, `BAAI/bge-small-en-v1.5`), Qdrant as the vector store, semantic search, and answer generation with a small local LLM (`qwen2.5:3b` through Ollama). First retrieval metrics: recall@k and MRR.
- **Cleaned up the structure (13–14 Oct)**: `src/` layout, a single config object (`pydantic-settings`), and tests separated from evaluation.
- **Chose a real corpus (16 Oct)**: three public football regulations — the IFAB *Laws of the Game 2026/27*, FIFA's *Regulations on the Status and Transfer of Players* (January 2025) and the *FIFA Disciplinary Code* (September 2025). A script downloads them from a manifest and checks each file's SHA-256, so the corpus is reproducible without committing the PDFs.
- **PDF extraction** with `pymupdf`: page numbers, running headers and side tabs are removed by their position on the page; section headings are detected (bold lines starting with an article number), and chapters come from the IFAB footer or the PDF's table of contents. Every passage is labelled, e.g. `Law 11 – Offside > 3. No offence`.
- **RAG on the real corpus (19 Oct)**: 1,289 chunks of 500 characters (50 overlap), each carrying its page and section; answers cite `[source, p. N]`.
- **Evaluation set and baseline (26–28 Oct)**: 85 questions with their expected passages. Each evaluation run is saved in `experiments/` with its config and per-question results.

## Results

Baseline run `baseline` — dense retrieval, `bge-small-en-v1.5`, 500-character chunks, k = 3, 84 answerable questions:

- **Recall@3: 0.7917**
- **MRR@3: 0.7183**

## Decisions

- **Football regulations as the corpus.** I am passionate about football and come from the football industry. Three PDFs is a small corpus, but a good base to start from.
- **Evaluation-driven development.** Every change to a part of the RAG will be measured against a fixed evaluation set, and kept only if the numbers justify it.
- **A passage is identified by `(source, section)`, not by chunk id.** Chunk ids change as soon as the chunking changes; sections do not, so the evaluation set stays valid across experiments.
- **The evaluation set was drafted by a strong model, not by the 3B one.** The 3B model wrote wrong answers when generating questions. Each generated question carries a verbatim quote from its passage, checked automatically, so the reference answers are grounded in the corpus.
- **English only, for now.** I want a clean English project first; multilingual can come later.

## What failed or surprised me

- **A flaky test.** A test asked the real 3B model to cite its source; it failed about one run in three. That is when I understood the difference between *tests* (is my code broken? deterministic, LLM mocked) and *evaluation* (how good is my system? scores).
- **Wrong assumptions in the PDF extraction**: an invisible control character (`\x07`) was first treated as a bullet point, and FIFA's website ignores the file name in its URLs, so the "January 2026" edition I thought I had downloaded was actually the January 2025 one. Both were caught by reading the extracted text, not by tests.
- **A French question found nothing.** Asking "qu'est-ce que la règle du hors-jeu" retrieved irrelevant passages: the embedding model is English-only, and very short chunks such as `Law 5 – The Referee (p. 73)` end up vaguely similar to every question. With French questions in the set, French recall@3 was 0.111.
- **The extracted text still contains non-breaking and thin spaces**, which break exact string matching.

## What I learned

- What RAG is and how its two halves fit together.
- Tests and evaluation answer different questions.
- Look at the data before writing code, and keep looking after: the worst bugs here were wrong assumptions about the data.

## How I used AI

I use Claude Code for development and I own that choice — at the end of 2026, writing everything alone without an agent no longer makes sense to me. Claude wrote most of the code (PDF extraction, evaluation, tests) and drafted the evaluation questions. I wrote parts myself, such as the passage sampling for question generation, and I made the calls: the domain, the scope, English only, and working evaluation-first. At one point I told Claude to stop writing code without me, because my goal is to understand every choice made in this project. It is a hybrid way of working.
